# TravelTech
**Куркина Татьяна Юрьевна. Проектирование сервиса планирования путешествий.**
## 1. Цель и назначение системы

**Цель:** разработать подсистему интеллектуального мониторинга авиарейсов, которая отслеживает изменения статусов перелётов пользователей, своевременно выявляет задержки и отмены, подбирает альтернативные варианты и автоматически актуализирует общий план путешествия.

Подсистема должна обеспечивать непрерывность путешествия даже при:

- задержке поступления информации от авиакомпаний;

- временной недоступности внешних API;

- отсутствии пользователя в сети;

- изменении расписания нескольких связанных рейсов;

- наличии ограничений по визам, багажу, пересадкам и часовым поясам.

### 1.1. Основные бизнес-цели
| № | Бизнес-цель | Ожидаемый результат |
| :--- | :---| :--- |
| 1 | Снизить влияние сбоев рейсов | Пользователь своевременно узнаёт об изменениях |
| 2 | Сократить время перепланирования | Альтернативы подбираются автоматически |
| 3 | Сохранить целостность поездки | Все связанные бронирования актуализируются |
| 4 | Обеспечить совместное планирование | Все участники поездки получают согласованную информацию |
| 5 | Защитить персональные данные | Паспортные данные удаляются после завершения необходимости их обработки |

### 1.2. Границы системы

**Входит в систему:**

- получение статусов рейсов;

- нормализация данных от разных авиакомпаний;

- обнаружение задержек, отмен и изменений;

- оценка влияния события на маршрут;

- поиск альтернативных рейсов;

- подбор альтернативных активностей;

- уведомление пользователей;

- обновление общего маршрута;

- ведение истории изменений;

- обработка ошибок внешних интеграций.

**Не входит в систему:**

- управление воздушным движением;

- самостоятельное управление расписаниями авиакомпаний;

- гарантированное оформление возврата средств авиакомпанией;

- автоматическое изменение оплаченных бронирований без соответствующего согласия пользователя;

- принятие решений о выдаче виз.

## 3. Функциональные требования
Система должна:

- регистрировать рейсы из подтверждённых бронирований;
- получать актуальные статусы рейсов через API;
- принимать события из email-рассылок авиакомпаний;
- обнаруживать задержку рейса;
- обнаруживать отмену рейса;
- обнаруживать изменение времени вылета, прилёта или аэропорта;
- оценивать влияние изменения на последующие сегменты маршрута;
- подбирать альтернативные рейсы;
- учитывать багаж, визы, транзитные ограничения и пересадки;
- учитывать интересы пользователя при подборе активностей;
- отправлять уведомления пользователям и участникам поездки;
- поддерживать отложенную доставку уведомлений при оффлайне;
- обновлять общий план путешествия после подтверждения изменений;
- хранить историю изменений маршрута;
- предотвращать дублирование уведомлений;
- обрабатывать недоступность внешних API;

## 5. Архитектура системы
Предлагается использовать событийно-ориентированную микросервисную архитектуру (Event-Driven Architecture).

Такой подход позволяет независимо обрабатывать поступающие статусы рейсов, уведомления и изменения маршрутов.

### 5.1. Основные компоненты
| № | Компонент | Назначение |
| :--- | :---| :--- |
| 1 | Flight Monitoring Service | Мониторинг зарегистрированных рейсов |
| 2 | Flight Data Adapter | Интеграция с API авиакомпаний и обработка email |
| 2 | Event Broker | Передача событий между компонентами |
| 2 | Flight Event Processor | Нормализация и обработка изменений статусов |
| 2 | Disruption Analyzer | Анализ влияния задержек и отмен |
| 2 | Alternative Search Service | Поиск альтернативных рейсов |
| 2 | Constraint Validator | Проверка виз, багажа, пересадок и других ограничений |
| 2 | Activity Recommendation Service | Подбор альтернативных активностей |
| 2 | Trip Planner Service | Обновление общего маршрута путешествия |
| 2 | Notification Service | Отправка уведомлений |
| 2 | User Preference Service | Получение предпочтений и настроек участников |
| 2 | Booking Service | Управление бронированиями |
| 2 | Data Storage | Хранение рейсов, маршрутов, событий и истории |

### 5.2. Принцип взаимодействия
1. Flight Monitoring Service получает информацию о рейсе.
2. Flight Data Adapter преобразует данные в единый внутренний формат.
3. Событие поступает в Event Broker.
4. Flight Event Processor проверяет событие на дублирование и актуальность.
5. Disruption Analyzer оценивает влияние изменения на путешествие.
6. Alternative Search Service ищет возможные варианты.
7. Constraint Validator проверяет допустимость альтернатив.
8. Notification Service информирует участников.
9. После согласования Trip Planner Service обновляет маршрут.

## 6. Основные бизнес-процессы
### 6.1. Процесс мониторинга рейса

**Предусловия:**

- пользователь зарегистрирован;

- поездка создана;

- рейс добавлен в поездку;

- имеется идентификатор бронирования или данные рейса;

- пользователь дал необходимые согласия на получение уведомлений.

**Основной сценарий:**

1. Система регистрирует рейс.

2. Сохраняет номер рейса, дату, аэропорты и идентификатор перевозчика.

3. Создаёт задачу мониторинга.

4. Периодически запрашивает статус рейса у внешнего API.

5. Получает информацию о статусе.

6. Сравнивает её с последним подтверждённым состоянием.

7. Если изменений нет — продолжает мониторинг.

8. Если обнаружено изменение — создаёт событие.

9. Передаёт событие в обработчик изменений.

**Альтернативный сценарий:**

Если API недоступен:

1. система фиксирует ошибку;

2. выполняет повторный запрос с увеличивающимися интервалами;

3. переключается на резервного поставщика данных, если он доступен;

4. использует email-уведомления как дополнительный источник;

5. помечает данные как устаревшие;

6. не сообщает пользователю неподтверждённую информацию как достоверную.


### 6.2. Процесс обработки задержки или отмены

1. Получено событие о задержке или отмене.

2. Проверяется достоверность и время события.

3. Определяется поездка и все связанные сегменты маршрута.

4. Рассчитывается влияние изменения на пересадки и последующие активности.

5. Если влияние отсутствует, пользователь получает информационное уведомление при необходимости.

6. Если влияние есть, система запускает поиск альтернатив.

7. Альтернативы проходят проверку ограничений.

8. Формируется список предложений.

9. Пользователь получает уведомление.

10. Пользователь выбирает вариант.

11. Система проверяет доступность выбранного варианта повторно.

12. При необходимости выполняется бронирование после подтверждения пользователя.

13. Общий маршрут обновляется.

14. Все участники получают информацию об изменениях.

## 7. Логика обнаружения задержек и отмен
### 7.1. Модель статусов рейса

Для унификации информации от разных авиакомпаний предлагается использовать внутренний справочник статусов.

| Статус | Значение |
| :---| :--- |
| SCHEDULED | Запланирован |
| CHECK_IN | Регистрация открыта |
| BOARDING | Посадка |
| DELAYED | Задержан |
| DEPARTED | Вылетел |
| IN_AIR | В полёте |
| LANDED | Приземлился |
| CANCELLED | Отменён |
| DIVERTED | Направлен в другой аэропорт |
| UNKNOWN | Неизвестен |

Система должна различать плановое и актуальное время вылета. 

### 7.2. Правила обнаружения событий

Примеры бизнес-правил:

| № | Условие | Действие |
| :--- | :---| :--- |
| 1 | Статус изменился на CANCELLED | Создать критическое событие |
| 2 | Задержка составляет 15 минут и более | Зафиксировать изменение |
| 3 | Задержка угрожает пересадке | Запустить срочный анализ маршрута |
| 4 | Изменился аэропорт прилёта | Пересчитать активности |
| 5 | Изменилось время прилёта | Пересчитать время последующих событий |
| 6 | Данные разных источников противоречат друг другу | Запустить дополнительную проверку |


### 7.3. Проблема задержанного поступления данных

Риск — ситуация, когда авиакомпания уже отменила рейс, но внешнее API ещё показывает старый статус.

Для решения необходимо:

- использовать несколько независимых источников;

- хранить время события и время его получения;

- учитывать версию данных;

- выполнять периодическую повторную проверку;

- применять механизм обнаружения пропущенных событий;

- отображать пользователю время последней проверки.

## 8. Алгоритм подбора альтернативных рейсов

Подбор альтернатив должен происходить не просто по совпадению аэропортов и времени, а с учётом всех ограничений путешественника.

### 8.1. Этапы подбора

**Этап 1. Формирование кандидатов**

Система ищет:

- прямые рейсы;

- рейсы с пересадками;

- рейсы в соседние аэропорты;

- рейсы других авиакомпаний;

- варианты с другим временем отправления.

**Этап 2. Проверка жёстких ограничений**

Альтернатива исключается, если:

- отсутствует возможность перевезти необходимый багаж;

- пассажир не имеет права на въезд или транзит через соответствующую страну;

- время пересадки меньше минимально допустимого;

- невозможно успеть на следующий сегмент;

- рейс недоступен для бронирования;

- не хватает мест на всю группу.

**Этап 3. Проверка мягких ограничений**

Оцениваются:

- стоимость;

- время прибытия;

- количество пересадок;

- авиакомпания;

- предпочтения пользователя;

- влияние на запланированные активности.

**Этап 4. Ранжирование**

Пример формулы оценки:

Score=0.35T+0.25C+0.20R+0.10B+0.10P

Где:

T — оценка удобства времени;

C — оценка стоимости;

R — оценка надёжности маршрута;

B — оценка соответствия багажным требованиям;

P — соответствие предпочтениям.

Каждая оценка нормализуется в диапазон от 0 до 100.

Коэффициенты являются примерными и настраиваются бизнесом. Визовые ограничения, минимальное время пересадки и наличие мест не должны компенсироваться высоким общим баллом: они проверяются отдельно как обязательные условия.

**8.2. Особенности работы с багажом**

Система должна различать:

- ручную кладь;

- зарегистрированный багаж;

- специальный багаж;

- необходимость повторной регистрации багажа при пересадке.

Также необходимо учитывать, оформлен ли единый билет или отдельные билеты. Минимальное время пересадки для самостоятельной пересадки должно быть рассчитано с дополнительным запасом.

**8.3. Особенности визовых ограничений**

Система должна проверять:

- гражданство путешественника;

- наличие действующей визы или права на безвизовый въезд;

- требования транзитной страны;

- необходимость выхода из транзитной зоны;

- необходимость смены аэропорта;

- требования к сроку действия документов.

**8.4. Подбор альтернативных активностей**

Если пользователь не успевает на запланированную активность, система:

1. Проверяет новое время прибытия.

2. Получает актуальное расписание активности.

3. Проверяет доступность мест.

4. Учитывает часы работы и часовой пояс.

5. Проверяет возможность переноса или отмены старого бронирования.

6. Предлагает замену или перенос.


## 9. Обновление общего плана путешествия

Общий план поездки представляет собой набор связанных объектов:

- авиаперелёты;

- отели;

- трансферы;

- активности;

- рестораны;

- участники;

- уведомления.

При изменении рейса система должна анализировать не только сам рейс, но и все зависимые события.

Важно использовать механизм версионирования маршрута.

Например:

- версия 1 — первоначальный маршрут;

- версия 2 — обнаружена задержка;

- версия 3 — пользователь подтвердил альтернативный рейс.

Каждое обновление должно быть атомарным в рамках одной операции изменения маршрута. Если обновить трансфер удалось, а отель — нет, система должна зафиксировать частичный результат и сообщить о необходимости дополнительного действия, а не создавать впечатление, что вся поездка успешно перепланирована.

## 10. Уведомления и работа оффлайн
### 10.1. Каналы уведомлений

| Канал | Назначение |
| :---| :--- |
| Push | Основной канал оперативных уведомлений |
| Email | Подробная информация и резервный канал |
| SMS | Критические изменения при отсутствии push-доступа |
| In-app | Отображение событий внутри приложения |

### 10.2. Логика уведомлений

Система должна поддерживать:

- приоритеты уведомлений;

- повторную доставку;

- дедупликацию;

- подтверждение получения;

- сохранение непрочитанных событий;

- отправку уведомлений всем участникам поездки согласно их настройкам.

### 10.3. Работа пользователя оффлайн

Если пользователь не подключён к интернету:

1. Система сохраняет событие в очереди уведомлений.

2. Выполняет отправку через доступные каналы.

3. Продолжает поиск альтернатив независимо от статуса пользователя.

4. Сохраняет актуальную версию маршрута на сервере.

5. При повторном подключении синхронизирует приложение.

6. Показывает все непрочитанные изменения.

Необходимо предусмотреть, что push-уведомление само по себе не гарантирует получение информации пользователем. Поэтому критические события должны иметь резервный канал связи, если он доступен и разрешён пользователем.

## 13. Работа с часовыми поясами

### 13.1. Принципы хранения времени

1. Все временные отметки событий хранятся в UTC.

2. Для каждого аэропорта сохраняется IANA Time Zone ID.

3. Пользователю время отображается в локальном часовом поясе соответствующего места.

4. При изменении часового пояса маршрут пересчитывается.

5. Учитываются переходы на летнее и зимнее время.

Система не должна рассчитывать длительность перелёта простым вычитанием локального времени. Расчёты выполняются по UTC.

Также необходимо хранить исходные данные расписания и временную зону, чтобы корректно отображать историю изменений.

## 14. Защита персональных данных и паспортной информации

Паспортные данные нельзя хранить дольше, чем это необходимо для поездки.

### 14.1. Принципы обработки

- Собирать только необходимые паспортные сведения.
  
- Запрашивать согласие на соответствующую обработку.
  
- Передавать сведения внешним сервисам только при наличии правового основания.
  
- Шифровать данные при передаче и хранении.
  
- Ограничивать доступ к данным по ролям.
  
- Не помещать паспортные данные в логи и уведомления.
  
- Удалять данные после завершения установленного срока необходимости.

Нельзя устанавливать единый срок хранения паспортных данных для всех случаев. Срок определяется целью обработки, требованиями законодательства и условиями перевозчика. После прекращения необходимости данные должны быть удалены, если нет другого законного основания для их хранения.

## 15. Отказоустойчивость и обработка ошибок

Система должна сохранять работоспособность при отказе внешних сервисов.

### 15.1. Возможные ошибки

| Ошибка | Реакция системы |
| :--- | :--- |
|Flight API недоступен	| Повторный запрос, резервный источник |
| API вернул ошибку 429	| Соблюдение Retry-After и ограничение запросов |
| Получено некорректное событие	| Карантин события, логирование ошибки |
| Повторное событие	| Дедупликация |
| Устаревшее событие | Игнорирование для обновления состояния |
| Booking API недоступен | Сохранение предложения, повторная проверка |
| Notification API недоступен |	Повторная доставка, резервный канал |
| Потеря интернет-соединения	| Сохранение изменений на сервере, последующая синхронизация
| Не удалось обновить маршрут	| Повтор операции с контролем версии |

### 15.2. Используемые механизмы

**Retry + Exponential Backoff**

Повторные запросы с увеличивающимся интервалом.

Значения должны настраиваться в зависимости от типа API и его ограничений.

**Circuit Breaker**

При многочисленных ошибках внешнего API временно прекращаются запросы, чтобы не перегружать сервис.

**Dead Letter Queue**

События, которые не удалось обработать после установленного числа попыток, попадают в отдельную очередь для последующего анализа.

**Idempotency**

Повторная обработка одного события не должна создавать дубликаты уведомлений, бронирований или изменений маршрута.

**Outbox Pattern**

При изменении маршрута событие об успешном обновлении записывается в транзакционную таблицу Outbox. Затем отдельный обработчик отправляет его в Event Broker. Это снижает риск ситуации, когда маршрут уже изменился в базе данных, но остальные сервисы не получили соответствующее событие.

## 16. Многопользовательский режим

Для семейных и групповых поездок необходимо предусмотреть единый согласованный маршрут.

### 16.1. Роли участников

| Роль	| Права |
| :--- | :--- |
| Owner |	Создание поездки, управление участниками и маршрутом |
| Admin	| Управление бронированиями и изменениями |
| Member | Просмотр маршрута, получение уведомлений, участие в согласовании |
| Viewer | Только просмотр |

### 16.2. Правила согласования изменений

1. Система обнаруживает проблему.

2. Формирует альтернативные варианты.

3. Проверяет ограничения каждого участника.

4. Если альтернативы подходят не всем, отображает это организатору.

5. Организатор выбирает вариант или запускает согласование.

6. При необходимости участники подтверждают изменение.

7. После согласования обновляется общий маршрут.

Необходимо проверять не только одного пользователя, а всю группу.

## 18. Бизнес-сценарии и User Stories

**US-01. Уведомление об отмене рейса**

Как путешественник, я хочу получать уведомление об отмене рейса, чтобы своевременно изменить свои планы.

Критерии приёмки:
- система обнаруживает отмену;
- создаётся событие отмены;
- определяется поездка пользователя;
- отправляется уведомление;
- событие сохраняется в истории;
- повторное событие не вызывает повторного уведомления.

**US-02. Подбор альтернативного рейса**

Как путешественник, я хочу видеть альтернативные рейсы, чтобы выбрать наиболее подходящий вариант.

Критерии приёмки:
- учитывается направление;
- проверяется доступность мест;
- учитывается количество пассажиров;
- проверяются багажные ограничения;
- учитываются визовые требования;
- рассчитывается время пересадки;
- варианты ранжируются по предпочтениям.
  
**US-03. Автоматическое обновление маршрута**

Как организатор поездки, я хочу, чтобы после согласования нового рейса связанные события маршрута обновлялись автоматически.

Критерии приёмки:
- пересчитывается время трансфера;
- проверяется время заселения в отель;
- проверяется актуальность активностей;
- создаётся новая версия маршрута;
- участники получают уведомления;
- история изменений сохраняется.

**US-04. Работа оффлайн**

Как путешественник, я хочу получить информацию об изменениях после восстановления соединения, чтобы не пропустить важные события.

Критерии приёмки:
- события сохраняются на сервере;
- уведомления не теряются;
- при подключении приложение синхронизируется;
- непрочитанные события отображаются пользователю;
- устаревшие данные не перезаписывают актуальные.

## 23. Итоговое описание решения
В рамках проекта предлагается разработать событийно-ориентированную подсистему TravelTech, которая обеспечивает полный цикл обработки изменений авиарейсов.

Основная логика работы:

**1. Мониторинг рейсов**
   
   Получение статусов от авиакомпаний, внешних API и email-источников.
   
**2. Обнаружение изменений**
   
   Сравнение актуального статуса с предыдущим, выявление задержек и отмен.
   
**3. Анализ влияния**
   
   Проверка пересадок, отелей, трансферов и активностей.
   
**4. Подбор альтернатив**
   
   Поиск рейсов с учётом багажа, виз, часовых поясов и предпочтений.
   
**5. Уведомление пользователя**
   
   Отправка информации через push, email или SMS.
   
**6. Подтверждение решения**
   
   Пользователь выбирает альтернативу и подтверждает необходимые действия.
   
**7. Обновление путешествия**
   
   Система синхронизирует бронирования, маршрут и расписание участников.
